# 2026-10-24: recall starvation on an HNSW path, spec 0007 Part B

Run `2026-10-24-9f826bfd` (harness `6cc841d`, clean tree; query embeds about $0.00012). It covers 61 unique questions: the 29 permissions-suite questions and the 33 v1.2 answerable rows, with row 5 in both. Each question runs for 6 personas, at k = 5 and 20.

## Setup
- **A separate copy (AC-17):** `make ann-build CONFIRM=1` copies the 22,378 `fixed-512-64` text-embedding-3-large@1536 rows into `ann.hnsw_chunks`, with each chunk's `allowed_groups`. It adds a single HNSW cosine index and no GIN index.
  - The copy took 2.0 s and the index 18.8 s (with `maintenance_work_mem` 1 GB, set for that transaction only).
  - The table is 180 MB (the vectors sit in TOAST) and the index 174 MB.
  - The production tables and `SEARCH` are unchanged. A test checks with EXPLAIN that `SEARCH` still sorts a sequential scan of `public.chunk_embeddings`, with the copy present.
- **Freshness:** `check_fresh` runs after `acl.check_stale`. It fails, naming `make acl` and then `make ann-build`, on any of:
  - a row count that differs from the source
  - an `allowed_groups` value that differs
  - an embedding that differs
- **Settings:** pgvector 0.8.7 at its defaults: m 16, ef_construction 64, `ef_search` 40, `max_scan_tuples` 20,000. Each HNSW setting runs in its own transaction with `enable_seqscan` off, and a run fails if the plan doesn't use the index (every persona and setting did).
- **Timing:** a warm-up pass runs first, then a timed pass. The timed pass is the one scored.

## Results
ANN recall is HNSW against the exact filtered top k, divided by min(k, |exact|). Fact recall is AC-12's authorized recall, with n = 32 for admin, 31 for us-ic, manager and contractor, 18 for agency and 17 for narrow, matching the spec.

**k = 20**, as ANN recall / mean returned / questions returning fewer than k:

| persona (visible) | exact | iterative off | strict_order | relaxed_order |
|---|---|---|---|---|
| admin (100%, ≈ permissions off) | 1.000 / 20 / 0 | 0.975 / 20 / 0 | 0.975 / 20 / 0 | 0.975 / 20 / 0 |
| us-ic (98.62%) | 1.000 / 20 / 0 | 0.866 / 17.8 / 15 | 0.964 / 20 / 0 | 0.971 / 20 / 0 |
| manager (98.73%) | 1.000 / 20 / 0 | 0.869 / 17.9 / 14 | 0.968 / 20 / 0 | 0.972 / 20 / 0 |
| contractor (98.31%) | 1.000 / 20 / 0 | 0.825 / 17.0 / 15 | 0.963 / 20 / 0 | 0.968 / 20 / 0 |
| agency (32.46%) | 1.000 / 20 / 0 | 0.305 / 6.1 / 56 | 0.902 / 20 / 0 | 0.947 / 20 / 0 |
| narrow (1.15%) | 1.000 / 20 / 0 | 0.179 / 3.6 / 61 | 0.962 / 20 / 0 | 0.995 / 20 / 0 |

**k = 5**, ANN recall with iterative scans off → relaxed_order:
- agency: 0.597 → 0.934
- narrow: 0.430 → 0.970
- the ~98% cluster: 0.94–0.97 → 0.977–0.980

The full tables are in the run's `summary.md`.

- **Starvation is real, and it reaches the ~98% personas.** With iterative scans off, HNSW returns at most `ef_search` (40) candidates and then filters them.
  - **Narrow** gets 3.6 of 20 results on average, and **agency** 6.1.
  - **us-ic** got fewer than 20 on 15 of 61 questions, even though it sees 98.6% of chunks. The suite's questions target restricted pages, so restricted chunks crowd their neighbourhoods. A share of the whole corpus understates the filter's local effect.
- **Iterative scans fix the count.** Both modes return k on every question.
  - relaxed_order comes within about 0.03 of admin's 0.975 ceiling for every persona.
  - strict_order is a little lower (agency 0.902).
- **Admin's 0.975 is the cost of HNSW itself, not of filtering.** Admin's filter removes nothing, and its three settings returned identical results, as expected. The ceiling comes from ef_search 40; a sweep is in the follow-ups.
- **Fact recall:**
  - With relaxed_order, it equals exact for every persona at both k.
  - With iterative scans off, it drops for narrow (k=5: 0.868 vs 0.926; k=20: 0.941 vs 1.000) and agency (k=20: 0.917 vs 1.000).
- **Latency, p50 / p95 ms at k=20:**
  - Exact search is about 225 / 250 for the ~98% cluster (a scan and sort over 22k vectors), 79 / 86 for agency, and 3.3 / 3.8 for narrow, where the planner filters on the GIN index first.
  - HNSW with relaxed_order is 2.1–4.2 p50. Its p95 rises with selectivity: narrow 15.6 and agency 5.0, against 2.3 for us-ic. strict_order's tails are the longest (narrow p95 25.0).
- **No exact ties** at rank 5 or 20 for any persona.

## Exact path vs `d83f3edc`
Admin's exact top 5 was identical on **31 of 33** rows. Both misses are near-ties under a freshly embedded query:
- **row 32:** ranks 3 and 4 swap. They were 0.49978 and 0.49986 in `d83f3edc`.
- **row 93:** a different chunk takes rank 5. Ranks 4 and 5 were 0.60781 and 0.60987.

This is consistent with OpenAI embeddings differing slightly between calls, not with a change in the code path: `SEARCH` is untouched, and the EXPLAIN and AC-9 tests pass. The Part A AC-9 run (`7ff9d687`) matched 33 of 33. The plan reported this check rather than failing on it, for this reason.

## Consequence (AC-19)
When production gets an ANN index, it should use `hnsw.iterative_scan = relaxed_order`. Partitioning by group isn't needed at these selectivity points: relaxed_order reaches admin's ceiling even at 1.15%. Recorded in [ADR-0021](../decisions/0021-permission-model.md) and linked from [ADR-0020](../decisions/0020-chunk-configs-coexist.md). There is no production change.

## Decisions during the build
- **Admin as the permissions-off proxy (Arun):** admin's exact results equal unfiltered exact (AC-9), and its HNSW filter removes nothing. No unfiltered SQL was added, so AC-8 keeps no exemption. When the `PERMISSIONS` flag is built, a true off row goes into this measurement (follow-up).
- **Ties:** a count only, with no tie-aware variant (Arun).
- **Query vectors are saved** in `runs/ann/query-vectors.jsonl`, keyed by (model, question). They are written before the measurement starts, so a failed run never pays twice, and a rerun embeds nothing.
- **The integration tests** build the real `ann` schema from seeded random vectors inside one rolled-back transaction, instead of using `pg_temp` as the plan said. This exercises the actual SQL constants and restores any real copy afterwards.

## Gate catches
- **Wrong size:** the first build reported the table as 3 MB. `pg_relation_size` leaves out TOAST, where the 1,536-dim vectors live. The build now uses `pg_table_size`.
- A free smoke run of the measurement (random vectors, 3 questions, written to the scratchpad) ran before asking for the paid OK, so no bug could surface after the embed.

## Limitations
- There is one HNSW build at the default parameters, and the latencies come from a laptop DB (Colima, 4 CPUs, 128 MB shared_buffers) at 22k rows. The relative ordering is the finding; the absolute milliseconds aren't.
- `runs/` isn't committed, so in a fresh clone the baseline comparison prints "not available".
